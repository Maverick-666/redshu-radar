# 红薯雷达分类与监控基础设计

- 日期：2026-09-10
- 状态：对话设计已确认，等待书面复核
- 前置规格：`2026-09-09-redshu-radar-mac-design.md`
- 公开依据：[冬青的红薯雷达开发提示词](https://github.com/dong-liudong/hongshuleida/blob/main/dq.md)

## 1. 目标

在不改变可信销量口径的前提下，为当前商品库增加稳定、可检索的两级分类、多标签和候选/监控边界，为后续店铺分析与笔记研究提供共享的组织基础。

本阶段完成后，用户应能：

1. 将商品归入一个“赛道 → 细分品类”。
2. 给商品添加多个标签。
3. 按商品、店铺、商品 ID、分类和标签检索。
4. 将商品在“候选”和“每日监控”之间切换。
5. 继续使用现有数据状态、人工阶段和数值排序，不产生第二套指标口径。

## 2. 已确认的产品选择

- 建设顺序：分类与标签 → 店铺聚合 → 笔记研究。
- 分类模型：每个商品只有一个赛道和一个细分品类；标签可以有多个。
- 编辑入口：复用现有商品详情抽屉，不新建分类管理页。
- 入库策略：手动添加默认进入监控；未来批量发现默认只进入候选库。
- 凭证边界：本阶段不需要或保存小红书登录凭证；未来如公开数据不足，可增加独立研究账号适配器，凭证只进入本机安全存储。
- 现有 16 个商品升级后继续监控，分类保持为空，等待用户确认。

## 3. 与冬青提示词的关系

冬青提示词的数据层覆盖商品、快照、设置、日志、删除记录、WAL、索引和自动迁移，并要求店铺分析从商品及快照聚合。

本设计遵循这些原则，但不会照搬未在当前 Mac 版本中需要的完整 Windows 实现。冬青提示词未定义分类、标签或笔记研究的数据结构，因此新增一个独立的人工组织层。

边界如下：

1. 监控事实层：现有 `products`、`snapshots`、`collection_runs` 和 `collection_attempts`。
2. 人工组织层：新增 `categories`、`tags` 和 `product_tags`。
3. 消费层：未来的店铺分析只读聚合事实层；未来的笔记研究独立存储内容情报，只通过稳定 ID 关联。

分类和标签不得进入销量快照。店铺分析不得保存另一份“店铺今日销量”。笔记数据不得影响销量排名。

## 4. 数据模型

### 4.1 `categories`

字段：

- `id`：稳定整数主键。
- `name`：用户可见名称。
- `normalized_name`：用于去重的规范化名称。
- `parent_id`：赛道为空；细分品类指向一个赛道。
- `created_at`、`updated_at`。

规则：

- 只允许两级：赛道和细分品类。
- 细分品类的父级必须是赛道，不能继续嵌套。
- 同一父级下的规范化名称唯一；赛道名称全局唯一。
- 商品只保存细分品类 ID，赛道由父级关系得出，不在商品行重复保存。

### 4.2 `tags`

字段：

- `id`：稳定整数主键。
- `name`：用户可见名称。
- `normalized_name`：全局唯一的规范化名称。
- `created_at`、`updated_at`。

规范化至少包含去除首尾空白、合并连续空白和统一英文大小写。重复创建时返回已有标签，不产生同义重复行。

### 4.3 `product_tags`

- `product_id`：引用 `products.item_id`。
- `tag_id`：引用 `tags.id`。
- 复合主键为 `product_id + tag_id`。
- 删除标签或解除商品标签时只清理关联，不触碰快照；商品删除继续沿用现有规则，不由本表改变。

### 4.4 `products`

- 新增可为空的 `category_id`，只允许引用细分品类。
- 继续使用现有 `enabled` 表示是否参加采集：`1` 为监控中，`0` 为候选。
- `decision_status` 继续表示观察、复核、测试、放弃或放大，与 `enabled` 独立。

## 5. 迁移策略

- 使用增量迁移创建新表、索引和 `products.category_id`。
- 延续当前项目的 `PRAGMA table_info`/存在性检查思路，迁移必须可重复启动。
- 不重写现有商品、快照、采集运行或人工判断。
- 当前 16 个商品的 `enabled` 保持不变，`category_id` 为空且无标签。
- 迁移与应用启动在同一数据库连接中完成；失败时回滚，不能留下半套分类结构。

## 6. 服务和接口边界

新增一个分类服务，负责名称规范化、层级校验、去重和商品关联。采集器和统计模块不依赖分类服务。

接口需求：

- 读取赛道、细分品类和标签列表及商品数量。
- 创建赛道、细分品类或标签。
- 扩展商品详情更新：接收 `category_id`、`tag_ids` 和 `enabled`，与现有人工判断字段在一次事务中保存。
- 商品列表结果携带赛道、细分品类和标签，供本地页面检索与筛选。

第一阶段继续一次加载本地商品列表并在浏览器内筛选。数据结构和接口不依赖这一实现；未来商品达到需要分页的规模时，可以把相同筛选语义移到服务端，无需迁移数据。

## 7. 页面与交互

主榜单仍是唯一工作中心。

顶部工具区：

- 保留现有搜索、数据状态和排序。
- 增加三个紧凑入口：赛道、细分品类、标签。
- 赛道与细分品类单选；标签允许多选。
- 激活筛选以“标签（2）”等计数呈现，不为每个值生成永久按钮。

榜单：

- 增加紧凑分类信息和监控状态。
- 每行最多展示两个标签，多余内容显示“+N”。
- 不在表格中行内编辑，避免与排序和打开详情冲突。

详情抽屉：

- 增加赛道、细分品类、标签和每日监控控件。
- 可从下拉入口创建缺失的分类或标签。
- 一次保存分类、标签、监控状态和现有人工判断。

## 8. 检索与组合规则

- 搜索框匹配商品名、店铺名、商品 ID、赛道、细分品类和标签。
- 赛道、细分品类、标签、数据状态和文本搜索先共同过滤，再执行现有数值排序。
- 多个标签采用 AND 语义，即商品必须同时具有全部选中标签。
- 选择赛道后，细分品类入口只展示该赛道下的值。
- 未分类商品可单独筛选。
- 修改分类或标签并保存后，当前检索结果立即重新计算。

## 9. 入库与监控规则

- 当前手动添加入口成功创建商品后，继续设置 `enabled=1` 并建立首条真实快照。
- 未来自动拓品或批量发现只能设置 `enabled=0`，先进入候选库。
- 启用候选后，下一次采集为其建立真实基线；不得以启用时间或空值伪造快照。
- 停用监控不删除商品、分类、标签、人工判断或历史快照。
- 每日与手动全量采集继续只读取 `enabled=1` 的商品。

## 10. 错误处理

- 不存在的分类、把赛道直接赋给商品、跨越两级的父子关系和不存在的标签 ID 返回明确验证错误。
- 分类、标签、监控状态和人工判断的保存使用单一事务：全部成功或全部保持原值。
- 创建重复规范化名称时复用已有记录。
- 页面保存失败时保留用户尚未提交的表单内容，并显示可读错误。
- 分类服务失败不得阻断采集任务；采集失败也不得改变分类和标签。

第一阶段不提供分类/标签删除、合并、重命名、批量编辑或 AI 自动分类。这些能力以后通过稳定 ID 增加，不需要改写商品历史。

## 11. 测试与验收

必须覆盖：

1. 现有数据库增量迁移后，16 个商品及全部快照、人工判断和 `enabled` 无损保留。
2. 两级分类约束、同级名称去重和标签规范化去重。
3. 商品分类与标签关联的新增、替换和清空。
4. 分类、标签、监控状态和人工判断的事务性保存。
5. 商品名、店铺、ID、分类名和标签名检索。
6. 赛道、细分品类、多标签、数据状态、文本搜索和排序的组合结果。
7. 多标签 AND 语义与未分类筛选。
8. 停用商品不进入采集，重新启用不生成假快照。
9. 榜单只展示两个标签和“+N”，筛选控件不随标签数堆积。
10. 原有测试继续通过，分类修改不改变任何销量指标或快照。

人工验收：用户能为现有商品完成分类，使用分类或标签检索出正确结果，并把一个商品在候选与监控之间安全切换。

## 12. 后续扩展边界

### 店铺分析

按 `shop_id` 聚合现有商品和可信快照，并允许按分类过滤。当前 16 个商品来自 16 家不同店铺，页面初期信息有限；不为填满页面而制造重复指标。

### 笔记研究

使用独立内容情报表，记录原始链接、标题、作者、公开互动信息、采集时间和研究备注，通过 `category_id` 或 `product_id` 关联。它不进入 `snapshots`。

### 登录采集

只有无凭证来源被实际证明不足时才新增适配器。届时使用独立低价值研究账号、系统安全存储、只读采集、频率限制和人工重新授权；Cookie、令牌或账号信息不得写入 SQLite 业务表、日志或 Git。

## 13. 明确不做

- 本阶段不实现店铺分析或笔记研究页面。
- 不接入 Spider_XHS 或复制其代码。
- 不实现自动拓品、AI 自动分类、批量标签治理或分类管理后台。
- 不引入账号凭证、远程服务或另一套指标计算。
- 不把分类、标签或人工判断当作市场事实。
